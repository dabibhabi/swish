## Experience improvements (second pass: `Renderer_Frame.cpp`, `Swapchain.cpp`, `WeatherController.cpp`, `IBLManager.cpp`, `Device.cpp`, `App.cpp`)

Ordered by how much a player would notice. None of these were measured; each is from reading the code.

- [ ] **E1. Weather change freezes the frame.** `App::on_cycle_weather` (`AppInput.cpp:84`) calls `WeatherController::set_preset`, which loads the HDRI from disk, calls `vkQueueWaitIdle`, and runs the convolution bake on the main thread (`IBLManager.cpp:426-449`; the procedural path at `IBLManager.cpp:453-478` does the same). The car keeps its speed but the picture stops for the length of the bake. `frame_delta` caps the step at 67 ms (`App.cpp:112`), so physics does not explode, but the sim visibly hitches.
  - **You:** press the weather key while driving in `make run` and note how long the stall is. This tells us whether E1 is worth the work.
  - **Edit (if it is):** the cheapest fix is to preload all preset HDRIs at startup (so the key press only swaps a cube), or spread the bake over several frames. A blending cross-fade is a bigger feature; do not start it without asking.
- [ ] **E2. Input is sampled before the vsync wait.** The loop in `App.cpp` (L88-99) reads keys and steps the car, then `drawFrame` blocks on `waitForFence` (`Renderer_Frame.cpp:27`). With FIFO vsync that wait can last most of a frame, so the input used for this picture is up to one frame old. For a driving sim that is extra steering lag.
  - **Edit:** add a small `Renderer::wait_frame_ready()` that does the fence wait, and call it at the top of the `App` loop before `frame_delta` and `poll_events`. Keep the existing wait in `drawFrame` (it becomes a no-op because the fence is already signalled).
  - **You:** compare steering feel before and after in the app. This is a feel test, so only you can judge it.
- [ ] **E3. A GPU hang looks like a frozen window.** The fence wait (`SyncObjects.cpp:53-54`) and `vkAcquireNextImageKHR` (`Renderer_Frame.cpp:58`) both use `UINT64_MAX` (no timeout). If the GPU hangs or the window is occluded and the drawable never returns, the app freezes with no message.
  - **Edit:** use a timeout of about 5 s. On `VK_TIMEOUT`, log which wait timed out and throw. Do not use the timeout for the minimised case: `recreateSwapchain` already handles that (see item 1).
  - **You:** I have not confirmed that MoltenVK blocks on an occluded window. If you see the app freeze when the window is fully covered, tell me; that makes E3 a Must fix.
- [ ] **E4. No frame-rate readout in release.** The GPU profiler and capture are debug-only (`SWISH_DEBUG_UI`). In `make run` you cannot see fps, so you cannot tell whether a build is hitching.
  - **Edit:** update the window title once per second with fps and frame time (`glfwSetWindowTitle`, cheap, no new UI). Keep it behind a config flag so the shipped title stays clean.
- [ ] **E5. Pipeline cache is saved only on clean exit, and not atomically.** `Device::savePipelineCache` (`Device.cpp:196-203`) opens the file with `trunc` and writes in place. A crash or force-quit during that write leaves a truncated file. Vulkan checks the header, but a short blob with a valid header is a risk you do not need.
  - **Edit:** write to `<path>.tmp`, then `std::filesystem::rename` over the real file. Optionally also save after the first full frame, so a crash later still keeps the cache.
  - **You:** after the edit, delete the cache file once and confirm the second launch starts faster than the first.
- [ ] **E6. Vsync is fixed on (`Swapchain.cpp:125-127`).** Fine for a sim. If you ever want a latency-test mode, make the present mode a config value, with FIFO as the fallback. Low priority; do not build it until you ask.
- [ ] **E7. Three swapchain images plus two frames in flight.** `Swapchain.cpp:24` asks for `minImageCount + 1`. On a typical 2-image minimum that is 3 images. This is the standard choice and I would leave it alone. If steering still feels late after E2, lowering it is the next thing to try, but only by measuring.

What I checked and found fine: the DT cap, the fence order (reset only after a successful acquire, so an out-of-date acquire cannot deadlock), the resize path (framebuffer size, not window size, so Retina is right), and that the pipeline cache is already persisted and validated on load.
