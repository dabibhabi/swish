# 🏎️ Turbo S physics · hydroplane spin-out · real-world LIE corridor — 3-phase plan (2026-08-23)

Three-phase plan from a full grilling session, sequenced **physics/speed accuracy → hydroplane
spin-out → real-world OSM/SUMO corridor** (user's explicit priority order). Each phase has its own
detailed design doc (reasoning, facts, math, diagrams, tools) and an owning agent.
**Phases 1, 2 and 3a all shipped 2026-08-23.** Phase 2 built on Phase 1's per-axle
load-transfer/friction-circle decomposition — and had to *extend* it (see its review note: the
spec's "just relax the yaw clamp" premise turned out to be measurably false).

- [x] **Phase 1 — Physics & speed accuracy** — **SHIPPED 2026-08-23** (owner:
      `vehicle-physics-engineer`). Full spec:
      [`docs/phase-1-physics-speed-accuracy.md`](../../archive/docs/phase-1-physics-speed-accuracy.md) (now
      carries a §8 "As built / measured"). Retargeted the car to a 911 Turbo S (AWD, ~1670 kg,
      478 kW/800 N·m, 7200 rpm redline) via a slip-responsive AWD PTU torque split against a
      per-axle friction circle with load transfer; parametric camber/toe curves + anti-roll bar as a
      cross-corner target shift (no runtime multibody solver); no launch-control/PSM state machine.
      **Release-visible change**, deliberately — no debug-only scaffolding added.
      - **Measured, emergent (nothing targets these numbers):** **0-60 = 2.758 s** vs the 2.8 s
        reference · 0-100 = 5.904 s · top speed **205.1 mph** analytic / **203 mph and climbing**
        in engine, in 7th at 6803 rpm (drag-limited, not rev-limited) · launch **1.050 g** · peak
        braking **1.064 g**. The 0-60 is 1.5% quick and that is *reported, not tuned away*: this
        model has no torque interruption across shifts and the sprint contains two upshifts.
      - **Reviewed / verified:** 116/116 ctest (was 82; +11 physics cases, 10 159 assertions across
        the 44 car/wheel cases); both configs build clean; camber/toe and FOV-kick both A/B'd with
        window-only screenshots in the **release** build; in-engine telemetry confirms the gear/rpm
        mapping exact at 128/170/177/203 mph; Phase-B `m_position`/`m_rotation` invariant grep clean.
      - **Deviations from the spec, all documented in §8:** front share capped at 0.50 rather than
        §4.1's literal 1.0 (a clutch pack cannot route all torque forward, and doing so would be
        *worse* than RWD once the front's circle applies); `s_rear/s_max` implemented as rear
        over-demand (§4.1's permitted proxy — there is no wheel-inertia state anywhere, so slip is
        never measurable); λ also gates cross-axle spill, which is what actually produces the AWD
        launch; camber/toe gains estimated from linkage-family behaviour because the GLB contains no
        suspension linkage to digitise and no public 992 hardpoint table exists.
      - **Closed the §7 risk:** GT3 ride rates (2.3/2.5 Hz) replaced with re-derived Turbo S values
        (1.8/2.0 Hz, ζ 0.45/0.50, ±45 mm) — stability margin *improved*, so no substepping change.
      - **Sequenced for Phase 2:** `axle_loads_long()` / `friction_circle_fx_max()` /
        `axle_lateral_forces()` are separate tested functions with the lateral term already a
        first-class input; Phase 2 extends the load transfer with the lateral ΔF_z term rather than
        re-deriving it.
      - **F1 (FOV kick + shake) needed no work** — already shipped 2026-08-15, and its speed
        normaliser `kMaxForwardSpeed` was already 92 000 WU ≈ 205 mph, i.e. already the Turbo S
        figure. Verified visually rather than rebuilt. Engine audio remains out of scope.
- [x] **Phase 2 — Hydroplane spin-out — SHIPPED 2026-08-23** (owner: `vehicle-physics-engineer`).
      Spec + as-built: [`docs/phase-2-hydroplane-spinout.md`](../../archive/docs/phase-2-hydroplane-spinout.md)
      (see its new **AS-BUILT** section). Tests **117 → 137**; both `SWISH_DEBUG_UI` configs build
      clean; visually verified at wetness 0 and 1.0; no debug scaffolding shipped.

      **Review — the spec's central premise was wrong, and the doc says so now.** "Relax the clamp
      and the tire-saturated model diverges" is measurably false: with *static* axle loads the
      saturated yaw moment is `a·μFzf − b·μFzr = 0` **identically** (each axle's load ∝ the opposite
      lever), so the model is yaw-*neutral*, not unstable. Measured: clamp on → 4.0 °/s peak yaw;
      clamp fully released → **2.4 °/s**. Four changes were actually needed — (1) close the friction
      circle longitudinal→lateral with load transfer, which makes the moment `−μ·m·a_x·h_cg` ≠ 0
      (exactly the extension Phase 1's own code comment predicted); (2) add the **missing** body-frame
      transport term `v̇x += v_l·r`, without which rotation spuriously creates/destroys kinetic energy;
      (3) release the quasi-steady yaw/sideslip clamps toward a kinematic pivot rail; (4) **rate-limit**
      how fast those bounds may tighten — found in a live run where the clamp re-engaging deleted real
      momentum (31.8 → 12.5 m/s in one 0.5 s sample, ~4 g no tire produced).

      Decision 2 ("hydroplane-only") is now **structural**: `effective_mu`'s own smoothstep is hoisted
      into `hydroplane_fraction()` (one definition of "planing"), every Phase-2 term is weighted by it,
      and it is exactly 0 on dry/merely-wet/slow-on-water. Verified with the flood forced on and
      wetness 0: `planeFrac = 1.00`, every term at full strength, car still tracks at 0.0° sideslip to
      163 mph.

      **§5 negative-v_x work — the spec was partly stale and there was a live shipped bug.**
      `max_yaw_rate` already had `fabs(vx)` (the `max(vx,1)` the spec quotes never existed) and needs
      no sign fix — it's symmetric in r. But `axle_lateral_forces` subtracted the steer term
      *unconditionally*, so at v_x < 0 it yawed the car **backwards**: −42.8° of heading in one second
      at 10 m/s reverse with 0.2 rad of steer. That was already reachable, since reverse tops out at
      12 m/s > the 5 m/s dynamic threshold. Fixed unconditionally (`sgn(vx)·δ`). Three more places
      assumed v_x ≥ 0 and would have eaten a spin: the `kMaxReverseSpeed` clamp, the dead-stop snap,
      and the `speed == 0` early return.

      **§4 tolerance table re-verified against the Phase-3a corridor** (it was written for the retired
      treadmill). Load-bearing correction: the world-X clamp is **disabled**
      (`CorridorDriver::place_at_start` → `set_road_bounds(-1e9f, 1e9f)`); the bound is a corridor-space
      `(station, lateral)` clamp that is **lane-count dependent** and opens to full width in the two
      U-turn pads. Measured live during a spin: `lat` pinned at exactly +1900 WU and station ran
      *backwards* 0.366 → 0.356 mi with the segment window unbothered — more tolerant than the
      treadmill, since `kChunksBehind` no longer exists. Wetness/puddles survived the road replacement
      (corridor bands are `MAT_ASPHALT`); verified live with `film` reaching 1.40.

      **Deliberate limits (doc §A7):** a reliable full 360° pirouette is *not* reachable in the shipped
      patchy puddle field — every tire force scales with μ, so at μ = 0.08 the ceiling on yaw
      acceleration is `2μmgab/(L·Iz) ≈ 0.5 rad/s²`. The visible spins come from yaw built on grip and
      then *undamped* by the water (correct phenomenology). A genuinely violent spin needs per-side
      water sampling or a combined-slip tire — both real rewrites, both left for a re-grill. Cheapest
      next step: a first-order lag on `filmOverTread`. Dry-road spin stays deferred (decision 2); it is
      now one line (drive `planeFrac` from tire saturation), and it was measured to work — and to make
      dry braking-while-steering spin the car, which is why it stayed gated.
- [ ] **Phase 3 — Real-world LIE corridor** (owner: `scene-road-engineer`, then
      `roadside-props-engineer` for signage and `traffic-engineer` for the later TraCI sub-phase).
      Full spec: [`docs/phase-3-osm-lie-corridor.md`](../../docs/phase-3-osm-lie-corridor.md) — now
      carries a §8 "As-built (stage 3a)". Replaces the endless fictional treadmill entirely with a
      compacted (16-20mi of a real ~31mi Manhattan→Suffolk-border stretch) OSM-derived corridor —
      SUMO `netconvert` for lane geometry now, TraCI traffic later; real interchange geometry at
      6 landmark anchors.
  - [x] **3a — bare compacted alignment — SHIPPED 2026-08-23.** Real Overpass extract + SUMO
        netconvert 1.27.1 → landmark-compacted alignment → new segment/tile mesh generator, drivable
        end to end. **17.994 mi** from 31.20 real (target 18, band 16-20 ✔) with **N = 900 m,
        W = 250 m, solved c = 0.1854**; lane count from netconvert puts the **3→4 change at 7.90 mi,
        the Queens/Nassau line**, as the spec predicted. 25 segments, 1,921 draw calls, 81 KB asset.
        `make test` 117/117 (was 82) at the time of landing; both build configs clean. (A later run
        shows 4 `test_car_physics.cpp` failures from the concurrent Phase 2 work — not Phase 3a; all
        25 corridor cases pass.)
        *Two things it changed under the spec, both flagged in §8.7 for review:* (1) §4.2 needed a
        **curvature floor** — compaction scales arc length but preserves heading, so $R' = Rf$ and
        uniform compression drove the tightest radius from a real 99 m to 46 m and inflated sub-500 m
        mileage 1.05 → 6.05 km, i.e. it invented corners; `f_i = max(w_i + c(1-w_i), min(1, R_floor/R_i))`
        with `R_floor = 500 m` fixes it and keeps `c` derived. (2) §7's precision estimate was off by
        1000× — 18 mi is **2.9e7 WU (ULP 2 mm)**, not 3e10 (ULP 2 m), so the origin rebase is *not*
        required; it is kept because it is free.

  - [ ] **3c — real exit-number signage + HOV lane markings.** Exit refs are in the OSM extract's

# 🚗 AI-generated modular car asset pipeline — PLANNED, nothing built (2026-08-23)

User wants to stop depending on downloaded car assets (today's Porsche is a messy, unnamed
Sketchfab GLB the loader has to reverse-engineer) and generate future cars themselves with AI
tools, built from the start as a **modular, consistently-named rig** (body / 4× wheel / steering
wheel / seats / 4× suspension / decorative engine) so every car shares one skeleton and the loader
can eventually resolve parts by name instead of by translation-clustering heuristics. Exterior
priority is photorealism (paint, panel gaps, PBR correctness); interior only needs to read
correctly (steering wheel + dashboard shaped right, not full detail).

Three-agent research pass (mesh-gen tooling · modular rig conventions · PBR clearcoat/flake
texturing), synthesized into [`docs/car-asset-pipeline.md`](../../docs/car-asset-pipeline.md).
**No code or assets changed.** Headlines: no AI tool does "photoreal car, one click" — Tripo3D has
the best quad topology/vehicle fit today, but real Blender retopo + interior modeling + Substance
re-texturing is still required; AI-baked albedo often has lighting baked in (breaks under Swish's
own CSM/SSAO/SSR/IBL) so every exported albedo needs an eyeball pass; glTF plain nodes (no
Armature/skin) are sufficient for all of Swish's rigid per-part articulation; flake sparkle should
stay a shader-side procedural parameter, never a baked texture; `KHR_materials_clearcoat` is the
right export target for clearcoat weight/roughness, but flake density/scale/color needs new fields
on this project's own `MaterialId` table since no glTF extension covers it.

- [ ] A/B Tripo3D and Hunyuan3D (free daily quota, clean quad output — added 2026-08-23) on a first
      exterior-shell generation; budget real Blender retopo time regardless of which wins.
- [ ] Build interior shapes (steering wheel + dashboard) to the naming convention in
      `docs/car-asset-pipeline.md` §2 — optionally as a dry run on the current Porsche asset first.
- [ ] Write the clearcoat + flake shader itself (already tracked as open item #1 below) before
      investing heavily in AI-paint re-texturing, so texturing targets real shader inputs.
- [ ] Export GLB from Blender, validate node names survive export, add a name-based loader path
      that falls back to today's heuristic — additive, not a rip-and-replace of the current loader.
- [ ] Wiper blade: hand-model (don't expect AI mesh-gen to nail thin hinge/rubber-insert geometry),
      two materials (arm vs rubber), and a deliberate WORLD_SCALE standoff gap from the windshield
      glass — see `docs/car-asset-pipeline.md`'s wiper subsection.

**Same-day follow-up (2026-08-23): roadside environment assets.** Added
[`docs/environment-asset-pipeline.md`](../../docs/environment-asset-pipeline.md) answering whether
trees/leaves/highway props should also be AI-generated. Short answer: **no, not the tree structure
itself** — AI mesh-gen tools are weak on organic branching geometry; the right pipeline is a
procedural trunk/branch generator (Botaniq/Sapling2) + AI- or Megascans-sourced leaf-card textures
+ a per-vertex wind shader, replacing the current `MAT_TREE` cross-billboard placeholder as roadmap
item **B2** (LOD/impostors) eventually calls for. Guardrails/lamps/signage are already procedural
C++ geometry and should stay that way — spend any AI effort there on PBR *texturing*
(`MAT_ASPHALT`/`MAT_METAL`/`MAT_SIGN_*`), not new meshes.

- [ ] Source/AI-generate leaf-card texture atlases (species-referenced: red maple/sweetgum/willow
      oak per NY DOT LIE roadside planting records) before attempting any tree mesh LOD.
- [ ] When picking up B2, treat it as "add a nearer mesh LOD that geomorphs into the existing
      billboard," not a billboard replacement.

# 🐞 Live-issue worklist — exposure · spray · sky/sun · 911 dynamics · speed feel · hydroplaning (2026-08-15)

From user screenshots + report. Source of truth: [`user-goals/CURRENT.md`](../../docs/user-goals/CURRENT.md)
("Reported issues to fix"). Each is debug-UI-tunable, release-safe, and **visually verified**
(screenshot at extremes) before it's checked off. Work with the noted specialist.

- [x] **1. Exterior over-exposed — road & sky blown out** — **FIXED 2026-08-15.** Root cause was NOT
      auto-exposure (that loop is `#ifdef SWISH_DEBUG_UI`, defaults off, never runs in release). It was six
      stacked multiplicative brightness lifts in the `lie preset`: exposure 1.6×, bloom 3.66×, sunAmbient
      2.35×, `SP_IBL_DIFFUSE` 1.83×, contrast 1.34×, and `SP_SHADOW_FLOOR = 1.0` (**shadow darkening
      disabled outright** — the CSM system contributed nothing). The magenta cast was a *consequence*:
      everything sat in AgX's per-channel clip, where whichever channel saturates first sets the hue.
      Unwinding the lifts removed the cast completely — that A/B is what proved the mechanism.
      Retuned to exposure 1.55 / bloom 0.45 / ambient 0.50 / IBL 1.30 / contrast 1.12, shadows restored
      (floor 0.25, bias 0.0018). AgX also made hue-preserving near the shoulder. (CHANGELOG.)
- [x] **2. Tire spray reads as fog, not water droplets** — **SHADER HALF DONE 2026-08-15.** Five
      structural causes found; four fixed in-shader: isotropic turbulence → velocity-aligned + decaying,
      2.6× billboard growth removed, velocity-aligned stretch added (area-neutral `pinch = 1/stretch`;
      an initial `1/sqrt(stretch)` was caught in adversarial review as still growing area ~73% at the cap),
      tighter radial falloff. **Still open:** the fifth cause — a single body-centre emitter spanning the
      whole car width. Per-wheel emitters need C++ plumbing (wheel world matrices are locals in

      opacity over it, replacing lit sky with flat asset tint and leaving only a `pow(NoH,256)` mirror
